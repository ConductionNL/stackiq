## Status: Oorzaak gevonden -- OPGELOST

Het probleem dat moduleB op "Select..." stond in de wizard terwijl er wel een applicatie B aanwezig was, is veroorzaakt door een verschil tussen hoe het koppeling-schema was gedefinieerd en hoe het oorspronkelijk bedoeld was. Dit is inmiddels opgelost door moduleB en buitengemeentelijkVoorziening weer als twee gescheiden velden te behandelen.

---

### Achtergrond: het Voorzieningen-model

Het datamodel van de Softwarecatalogus is gebaseerd op het [Gemeenschappelijk Informatiemodel voor Voorzieningen (GIMV)](https://www.noraonline.nl/wiki/Gemeenschappelijke_Informatiemodel_voor_Voorzieningen) van NORA. Het GIMV-model kent het concept "Koppeling" als een specialisatie van Voorzieningversie die twee entiteiten met elkaar verbindt.

> Bron: [Alliantie Voorzieningencatalogus](https://alliantie.github.io/voorzieningencatalogus/)

Belangrijk: het GIMV-model maakt **geen** expliciet onderscheid tussen interne koppelingen (applicatie ↔ applicatie) en externe koppelingen (applicatie ↔ buitengemeentelijke voorziening). Dat onderscheid is door de Softwarecatalogus zelf toegevoegd, met een duidelijk ontwerp:

- **moduleB** → verwijst naar een `module` (applicatie) in het voorzieningen-register
- **buitengemeentelijkVoorziening** → verwijst naar een `element` in het AMEF-register (landelijke voorzieningen zoals DigiD, GBA-V, BAG, BRP)

De [conceptdocumentatie (K005-koppeling)](../website/docs/Concepten/K005-koppeling.md) en de [schemadocumentatie](../website/docs/Softwarecatalogus/koppeling.md) bevestigen dit ontwerp:

> *"Koppelingen beschrijven de technische integraties tussen applicaties (modules) onderling en/of met buitengemeentelijke voorzieningen."*
> *"Er moet óf ModuleB óf buitengemeentelijkVoorziening gevuld zijn."*

---

### Wat er mis ging: chronologie van de schemadefinitie

De git-historie van `stackiq/lib/Settings/softwarecatalogus_register.json` laat zien hoe de definitie afweek van het ontwerp:

| Datum | Commit | Wijziging |
|-------|--------|-----------|
| 2025-08-20 | `879809f` | **Oorspronkelijk correct**: `moduleB` → `$ref: module`, `buitengemeentelijkVoorziening` → `$ref: element`. Twee gescheiden velden. |
| 2025-11-03 | `d3cd5b2` | **Afwijking**: `moduleB` krijgt een `items.oneOf` wrapper waardoor het ZOWEL een `module` ALS een `element` kan refereren. De top-level `$ref` en `objectConfiguration` worden verwijderd. |
| 2026-02-19 | `4d2464c` | `buitengemeentelijkVoorziening` krijgt `visible: false` (verborgen in UI) als onderdeel van een bulk-update. |
| 2026-03-02 | `f40cace` | **Correctie**: `oneOf` verwijderd uit `moduleB`, teruggezet naar simpele `$ref: module`. `buitengemeentelijkVoorziening` weer zichtbaar gemaakt (`visible: false` verwijderd). |

#### Het probleem: commit `d3cd5b2` (2025-11-03)

De commit met bericht *"Updated moduleB to ensure that it can be a module or a element"* veranderde moduleB van:

```json
"moduleB": {
  "type": "object",
  "objectConfiguration": { "handling": "related-object" },
  "$ref": "#/components/schemas/module",
  "title": "Module B"
}
```

naar:

```json
"moduleB": {
  "type": "object",
  "items": {
    "oneOf": [
      { "objectConfiguration": { "handling": "related-object" }, "$ref": "#/components/schemas/module" },
      { "objectConfiguration": { "handling": "related-object" }, "$ref": "#/components/schemas/element" }
    ]
  },
  "title": "Module B"
}
```

Dit had de volgende gevolgen:

1. **Import-verwarring**: De CSV-import mapt `moduleB` naar het veld, maar het veld accepteert nu zowel module-UUIDs als element-UUIDs. Voor de 876 koppelingen met een buitengemeentelijke voorziening wordt het element-UUID in `moduleB` gezet, terwijl `buitengemeentelijkVoorziening` leeg bleef.

2. **Wizard-dropdown "Select..."**: De wizard toonde een samengevoegde dropdown met zowel modules als elementen. Bij het bewerken van een bestaande koppeling kon het UUID niet altijd worden gematcht: als het UUID een element was maar de dropdown op "modules" stond, toonde het "Select...".

3. **Naamgeneratie-verwarring**: Het `objectNameField` template `{{ moduleA }} → {{ moduleB | buitengemeentelijkVoorziening }}` valt terug op `buitengemeentelijkVoorziening` als `moduleB` leeg is. Maar door de `oneOf` wijziging werd alles in `moduleB` gestopt, waardoor de naamlogica anders werkte dan bedoeld.

### Docs-schema vs. Live-schema

De gepubliceerde schemadocumentatie (in `website/static/api/softwarecatalogus_register.json`) heeft altijd het **correcte** ontwerp gehad — twee gescheiden velden:

```
Docs (correct):
  moduleB         → $ref: module     (alleen applicaties)
  buitengemeentelijkVoorziening → $ref: element   (alleen externe voorzieningen)

Live (was fout, nu gecorrigeerd):
  moduleB         → oneOf: [module, element]  ← FOUT (nu gecorrigeerd naar $ref: module)
  buitengemeentelijkVoorziening → visible: false  ← FOUT (nu weer zichtbaar)
```

### CSV-importdata analyse

Het importbestand `koppeling.csv` heeft gescheiden kolommen voor beide velden:

- **moduleB**: gevuld in 2.509 van 3.406 koppelingen (73,7%)
- **buitengemeentelijkVoorziening**: gevuld in 876 van 3.406 koppelingen (25,7%)
- **Beide leeg**: 21 koppelingen (0,6%)

Alle moduleB-UUIDs verwijzen naar bestaande modules (100% geldig). De 876 buitengemeentelijkVoorziening-UUIDs verwijzen naar 34 unieke GEMMA ArchiMate elementen (DigiD, GBA-V, BAG, BRP, etc.).

De CSV-data is dus correct opgezet met twee gescheiden kolommen — het probleem was dat het live schema deze niet correct als twee gescheiden velden behandelde.

---

### Oplossing

De schema-correctie (commit `f40cace`, 2026-03-02) herstelt het oorspronkelijke ontwerp:

1. **moduleB**: terug naar simpele `$ref: "#/components/schemas/module"` (alleen applicaties)
2. **buitengemeentelijkVoorziening**: `visible: false` verwijderd, `table.default: true` toegevoegd (zichtbaar in UI en tabel)
3. **Frontend**: wizard toont twee aparte velden in plaats van een samengevoegde dropdown

Na deze wijziging:
- Import mapt `moduleB` correct naar module-referenties en `buitengemeentelijkVoorziening` naar element-referenties
- De wizard toont geen "Select..." meer voor bestaande koppelingen
- Naamgeneratie werkt correct met het fallback-patroon `{{ moduleB | buitengemeentelijkVoorziening }}`
