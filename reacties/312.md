## Status: Datakwaliteit importbestanden + Code-beperking -- GEDEELTELIJK BEVESTIGD

Dit gedrag wordt veroorzaakt door een combinatie van ontbrekende data in het importbestand en een beperking in het importproces.

### Verificatie-methode

1. CSV-brondata geanalyseerd (`koppeling.csv`)
2. Koppeling-schema configuratie geanalyseerd (schema ID 18)
3. OpenRegister `MetadataHydrationHandler` code geanalyseerd
4. API-verificatie met vergelijking `naam` vs `@self.name`

### Bewijs: twee verschillende name-resolution paden

Het koppeling-schema heeft twee naamgeneratie-mechanismen:

**1. Property default (het `naam` business-veld):**
```json
{
  "default": "{{ moduleA }} {{ gegevensuitwisselingRichting | map: AnaarB=→, BnaarA=←, bi-directioneel=↔ }} {{ moduleB | buitengemeentelijkVoorziening }}",
  "defaultBehavior": "falsy"
}
```
Dit wordt toegepast wanneer de CSV geen `naam` kolom bevat. Bij CSV-bulkimport worden de `{{ moduleA }}` placeholders vervangen door de RAW UUID-waarde, omdat de relatie-objecten op dat moment niet worden geresolved.

**2. ObjectNameField (@self.name metadata):**
```
objectNameField: "{{ moduleA }} {{ gegevensuitwisselingRichting | map: ... }} {{ moduleB | buitengemeentelijkVoorziening }}"
```
Dit wordt verwerkt door `MetadataHydrationHandler.resolveRelationValue()` die WEL UUID-naar-naam resolutie uitvoert via de CacheHandler.

### Bewijs: API-vergelijking

```
GET /api/objects/voorzieningen/koppeling?moduleA=970cf3e9-57d2-563e-8cfe-8fab173f0438

Resultaat:
  naam (business data):  "970cf3e9-57d2-563e-8cfe-8fab173f0438 →"  <- UUID
  @self.name (metadata): "Gouw Belastingen →"                      <- Correct geresolved

Module 970cf3e9 bestaat WEL in het systeem:
  GET /api/objects/voorzieningen/module/970cf3e9-57d2-563e-8cfe-8fab173f0438
  -> naam: "Gouw Belastingen"
```

### Analyse van UUID-in-naam

Uit een steekproef van 200 koppelingen in het live systeem:
- **178 (89%)** hebben een UUID in het `naam` veld
- **22 (11%)** hebben een correcte naam (handmatig aangemaakt via wizard of bewerkt)
- Alle moduleA/moduleB UUIDs bestaan WEL in module.csv en in het live systeem

### Root cause

Dit is GEEN orphaned reference probleem. Het is een import-timing probleem:
1. **Datakwaliteit:** koppeling.csv bevat geen `naam` kolom, dus het schema-default wordt gebruikt
2. **Code-beperking:** het property-default template vervangt `{{ moduleA }}` door de rauwe UUID-string, niet door de geresolvede module-naam. De `resolveRelationValue()` methode in MetadataHydrationHandler wordt WEL aangeroepen voor `@self.name` maar NIET voor het property-default mechanisme

### Conclusie

**GEDEELTELIJK DATAKWALITEIT, GEDEELTELIJK CODE-BEPERKING:**
- **Datakwaliteit:** Het importbestand bevat geen `naam` kolom, dus naamgeneratie is nodig
- **Code-beperking:** Het property-default mechanisme resolved geen relatie-UUIDs naar namen bij import. Het `@self.name` metadata-veld doet dit WEL correct.
- **Geen orphaned references:** Alle moduleA/moduleB UUIDs verwijzen naar bestaande modules

### Aanbeveling
1. **Data:** Voeg een `naam` kolom toe aan het importbestand
2. **Code:** Zorg dat het property-default mechanisme dezelfde UUID-resolutie toepast als de objectNameField (via `resolveRelationValue`)
3. **Workaround:** Een bulk-update van alle koppelingen zou de namen kunnen regenereren op basis van de nu-werkende @self.name logica
