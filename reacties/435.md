## Status: Opgelost

### Samenvatting

Het probleem dat niet alle Centric-applicaties zichtbaar waren op de organisatiepagina is **opgelost**. De oorzaak was een hardcoded limiet van 30 in de backend-API voor het ophalen van gerelateerde objecten. Centric heeft 39 applicaties, waardoor er 9 werden afgekapt.

---

### Probleem

Op de organisatiepagina van Centric werden slechts 30 van de 39 applicaties getoond. Het tabblad toonde "Applicaties (30)" in plaats van "Applicaties (39)".

Dit was reproduceerbaar op zowel de lokale als accept-omgeving.

---

### Analyse

**Backend:** In `openregister/lib/Service/Object/RelationHandler.php` (regel 873) staat een fallback-limiet:

```php
$limit = $query['_limit'] ?? 30;
```

Wanneer de frontend geen `_limit` parameter meestuurt, valt de API terug op een maximum van 30 resultaten. De `/uses` en `/used` endpoints van publicaties gebruiken deze `RelationHandler::getUsedBy()` methode.

**Frontend:** De meeste publicatiepagina's stuurden geen `_limit` parameter mee bij het ophalen van gerelateerde objecten via de `/uses` en `/used` endpoints. Hierdoor werd de backend-fallback van 30 actief.

**Verificatie met curl:**

```
# Zonder _limit (fallback 30):
GET /api/publications/{id}/used?_extend[]=_schema
-> total: 30 (afgekapt!)

# Met _limit=100:
GET /api/publications/{id}/used?_extend[]=_schema&_limit=100
-> total: 39 (alle resultaten)
```

---

### Oplossing

`_limit=100` toegevoegd aan alle frontend fetch-calls voor `/uses` en `/used` endpoints. Hierdoor wordt de backend-fallback van 30 niet meer getriggerd.

**Gewijzigde bestanden:**

| Bestand | Wijziging |
|---------|-----------|
| `tilburg-woo-ui/src/constants/endpoints.constants.js` | `USED` endpoint constant |
| `tilburg-woo-ui/src/views/ac-publication/ac-publication-organisation.js` | uses + used inline fetch |
| `tilburg-woo-ui/src/views/ac-publication/ac-publication-module.js` | uses + used inline fetch |
| `tilburg-woo-ui/src/views/ac-publication/ac-publication-default.js` | uses + used inline fetch |
| `tilburg-woo-ui/src/views/ac-publication/ac-publication-koppeling.js` | uses + used inline fetch |
| `tilburg-woo-ui/src/views/ac-publication/ac-publication-contactperson.js` | uses + used inline fetch |
| `tilburg-woo-ui/src/views/ac-publication/ac-publication-gebruik.js` | uses + used inline fetch |
| `tilburg-woo-ui/src/views/ac-publication/ac-publication-dienst.js` | uses + used inline fetch |
| `tilburg-woo-ui/src/views/ac-beheer/domains/ac-organisatie/con-organisatie-details-page-content.js` | uses inline fetch |
| `tilburg-woo-ui/src/views/ac-beheer/core/components/custom/con-my-organisation.js` | uses + used inline fetch |

---

### Bewijs

Na de fix toont de Centric organisatiepagina correct:
- Tabblad: **"Applicaties (39)"** (was: "Applicaties (30)")
- API response `uses`: 2 resultaten (ongewijzigd, er zijn maar 2)
- API response `used`: **39 resultaten** (was: 30)
- Geen console errors

---

### Eerdere analyse (achterhaald)

Een eerdere analyse wees op duplicaat-data op de accept-omgeving als oorzaak. Dit was een separaat probleem. De werkelijke oorzaak van het ontbreken van applicaties was de hardcoded limiet van 30 in de backend.

---

### Opmerking over duplicaat-data (accept-omgeving)

Op de accept-omgeving bestaan dezelfde 39 Centric-modules dubbel onder twee verschillende organisatie-UUIDs (`8654869d` en `db36f8ab`). Dit is een apart data-import probleem en heeft geen invloed op de fix van dit issue. Het opschonen van deze duplicaten wordt separaat opgepakt.

---

### Achtergrond: CSV-importdata evolutie

De importdata komt uit [VNG-Realisatie/Softwarecatalogus-datamigratie](https://github.com/VNG-Realisatie/Softwarecatalogus-datamigratie/tree/main/data). Analyse van de volledige git-historie van `data/module.csv` laat zien hoe de `@self.organisation` toewijzing voor Centric-modules is geëvolueerd:

| Datum | Commit | Modules met @self.organisation = Centric | Toelichting |
|-------|--------|------------------------------------------|-------------|
| 2025-08-21 | `c0cd790` | 0 | Kolom `@self.organisation` pas net toegevoegd, Centric UUID nog niet ingevuld |
| 2025-08-29 | `5f8ed24` | **268** | Alle Centric-gerelateerde modules krijgen Centric's org UUID — inclusief gemeente- en samenwerkingsmodules |
| 2025-09-18 | `4a72088` | **267** | Idem, minimale wijziging |
| 2025-10-13 | `98c5a96` | **270** | Idem, nog steeds alles onder Centric |
| 2025-11-03 | `a99fe47` | **39** | Correctie na SQL-scripts + OpenRefine. Kolom `geregistreerd_door` toegevoegd. Alleen Leverancier-modules behouden Centric's UUID |

**Wat er gebeurde op 2025-11-03:**

Van de 270 modules die eerder `@self.organisation = Centric` hadden:
- **39 bleven** bij Centric (alle `geregistreerd_door = Leverancier`) — dit zijn Centric's eigen producten
- **171 verhuisden** naar de correcte organisatie-UUID van de registrerende partij:
  - 152 → `geregistreerd_door = Gemeente`
  - 19 → `geregistreerd_door = Samenwerking`
- **60 verdwenen** volledig (opgeschoond als duplicaten door OpenRefine)

**Conclusie:** Er is nooit een versie geweest van de CSV waarin `@self.organisation = Centric` en `geregistreerd_door ≠ Leverancier` in dezelfde rij voorkwam. De `geregistreerd_door` kolom is toegevoegd in exact dezelfde commit als de correctie van `@self.organisation`. Vóór die correctie hadden alle 270 Centric-gerelateerde modules (onterecht) Centric's UUID, ongeacht wie ze had geregistreerd.

Het oorspronkelijke verschil van "32 vs 39" dat in het issue wordt gemeld werd veroorzaakt door de frontend-beperking: de backend-fallback van `_limit=30` kapte de resultaten af. De oude softwarecatalogus toonde alle 39 omdat die een ander query-pad gebruikte zonder deze limiet. De fix (zie sectie "Oplossing" hierboven) voegt `_limit=100` toe aan alle frontend fetch-calls, waardoor alle 39 applicaties weer correct worden getoond.
